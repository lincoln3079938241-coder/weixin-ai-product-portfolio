AI AGENT · PRODUCT EVIDENCE

Auto-LifeOS

Turns a meal request into an executable workflow with deterministic validation, two-stage confirmation, and transactional inventory updates.

Public demo ↗ GitHub ↗
User problem

Recommendations ignore household inventory

Users still need to verify stock, expiry status, dietary restrictions, and actual quantities used.

Product goal

Make advice actionable, controlled, and reversible

A natural-language request must pass retrieval, deterministic validation, and two explicit confirmations before any inventory transaction.

Evidence

End-to-end flow + 61 tests

The live interface covers plan generation, quantity confirmation, inventory updates, and undo. Tests cover rule and transaction boundaries.

Product Evidence

Screenshots are taken from the currently deployed public demos. Some interface content remains in Chinese. Select an image to view it at full size.

Key Product Decisions

01

Two-stage confirmation

Plan approval and actual-quantity approval are separate, so generated advice cannot directly change inventory.

02

Model-rule separation

The provider interprets requests and structures plans. Deterministic rules control allergies, exclusions, expiry, quantity, and units.

03

Reversible side effects

Inventory updates use atomic transactions. Failures roll back; successful updates retain an audit record and support undo.

04

Stable public demo

The public version uses a Mock Provider and no private key. It does not claim to call a live foundation-model API.

Request→Intent→Retrieve & generate→ Validate→Two confirmations→Inventory transaction→Trace & undo

SYNTHETIC USABILITY EVALUATION

Simulated usability evaluation

Synthetic personas and task walkthroughs · Not interviews, experiments, or an A/B test

The evaluation identifies interaction friction and next-step hypotheses. It does not produce a sample size, conversion rate, or statistical-significance claim.

Single professional

Use soon-to-expire ingredients quickly

Friction: The reason for two confirmations may be unclear.

Current: Four-step progress reveals when the side effect occurs.

Next: Clarify the transition between confirmations.

Fitness-focused user

Understand protein and calories

Friction: Recommendation rationale may feel opaque.

Current: Shows nutrition estimates and a “why recommended” explanation.

Next: Surface the inventory items and rules used.

User with allergies

Prioritize safety constraints

Friction: Standard alerts may not be prominent enough.

Current: Deterministic rules block allergy and exclusion conflicts.

Next: Raise the visual priority of safety constraints.

Household inventory owner

Keep shared inventory accurate

Friction: Unit mismatches can make a plan non-executable.

Current: Validates units and updates inventory transactionally.

Next: Offer actionable unit-correction guidance.

A/B-style Prototype Comparison

This is a conceptual comparison, not a live traffic experiment or a real-user A/B test.

Heuristic Version A · Standard confirmation Version B · Two steps + inventory preview
Flow clarityPurpose of confirmation is unclearSteps 1/2 and 2/2 are visible
Risk visibilityTiming of the side effect is hiddenProjected changes appear before execution

DATA AUTOMATION · PRODUCT EVIDENCE

2027 Graduate Job Radar

Turns fragmented recruitment entry points into a traceable, filterable, and reviewable job-information list.

Public demo ↗ GitHub ↗
Pain point

High cross-platform search cost

Entry points are scattered, forcing repeated browsing and manual note-taking.

Pain point

Important details are easy to miss

Location, function, recruitment stage, and degree constraints lack a consistent structure.

Data problem

Source status is unclear

Reposted information may be duplicated or stale, so verification clues must remain visible.

Product value

Structure once, filter repeatedly

Convert public leads into a structured list and reduce repeated manual work.

Product Evidence

Screenshots are taken from the currently deployed public demos. Some interface content remains in Chinese. They show the implemented redacted-sample mode.

Key Product Decisions

01

No success-probability score

The available data cannot support a credible probability model, so the product provides source, filtering, and quality information only.

02

Retain source and time

Preserve source entry points, update times, and verification status wherever possible so users can return to official pages.

03

“Unknown” is an explicit state

Missing, failed, or unverified fields remain unknown or pending review. The product does not invent conclusions.

04

Graceful public fallback

Without a database or external interface, the public demo enters redacted-sample mode instead of failing and clearly states the data boundary.

Public entry points→Compliant collection/import→Clean & normalize→ Deduplicate & diff→Rule-based filters→Quality notices→Source review

Simulated usability evaluation

Synthetic personas and task walkthroughs · Not interviews or experiments

Company-type explorer

Compare SOEs, multinationals, and tech firms

Keep company type and source visible; use a consistent, prominent unknown state.

Time-constrained candidate

A multimodal mobility-assistant concept for automotive AI and Physical AI scenarios.

Target user

Urban commuter

Target user

Family traveler

Target user

Long-distance EV driver

JTBD

Key Product Decisions

01

Focus on compound tasks

Narrow a general-purpose assistant into a mobility task assistant.

02

Separate information layers

Present vehicle facts, external data, and model inferences separately.

03

No direct vehicle control

The agent does not execute high-risk vehicle operations.

04

Confirm before action

Key plans and reminders require user confirmation before execution.

05

Validate planning first

The MVP tests integration, explanation, and planning—not vehicle control.
