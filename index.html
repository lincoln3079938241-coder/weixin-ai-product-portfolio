01 / CORE CASE

AI AGENT · PUBLIC DEMO

Auto-LifeOS

把饮食需求变成经过规则校验、双阶段确认和库存事务更新的可执行流程。

公开Demo ↗ GitHub ↗
用户问题

饮食建议与家中食材脱节

用户得到一道菜后，仍需自行核对库存、过期状态、忌口和实际用量；文字建议也不应直接修改库存。

产品目标

让建议可执行、可控、可回退

自然语言需求经过检索、方案生成和确定性校验，只有两次明确确认后才触发库存事务。

公开边界

默认Mock，无需私密Key

公开版强制使用可复现Mock，不声称正在调用GPT、Qwen或其他真实模型；全部数据为synthetic/sample。

核心功能

  • LangGraph节点编排、条件路由、校验重试与异常回退
  • TF-IDF知识检索与结构化MealPlan
  • 库存、过敏、忌口、过期、单位和数量规则校验
  • 方案确认 + 实际用量确认的双阶段确认
  • SQLite原子库存事务、审计记录与撤销
61公开版测试通过 27核心仓库测试通过 28结构化演示菜谱

用户流程与Agent架构

需求输入→意图理解→检索与生成→ 规则校验→双确认→库存事务→追踪与回退
PROVIDER / MOCK

提出结构化方案

理解需求、组织检索证据、输出候选MealPlan；不拥有库存写权限。

RULES

控制可执行性

Pydantic与Python规则校验过敏、忌口、过期、单位、数量和营养范围。

TRANSACTION

控制副作用

双确认后由SQLite原子事务更新；失败整体回滚，成功结果可撤销。

TEST & BAD CASE

评测不是“看起来能跑”

自动化测试覆盖路由、别名、规则边界、双确认、事务原子性、撤销与会话隔离。合成Prompt对比观察结构解析、规则通过、幻觉食材、重试与可执行性；明确不等同于真实用户A/B测试。

结构不合法库存不足过敏/忌口食材过期 单位不兼容需求不清事务失败
02 / 0→1 DATA PRODUCT

DATA AUTOMATION · PUBLIC DEMO

2027届秋招岗位雷达

从分散招聘入口到可追溯、可筛选、可复核的岗位信息清单。

公开Demo ↗ GitHub ↗
痛点

跨平台搜索成本高

企业官网、公共就业服务和高校网站入口分散。

痛点

岗位信息容易遗漏

地点、方向、阶段和专业限制缺少统一表达。

数据问题

来源与状态不透明

转载可能重复或过时，需要保留来源与更新时间。

产品价值

一次整理，持续筛选

将公开线索转成结构化清单，降低重复劳动。

核心能力

  • 多来源配置与合规采集框架
  • 清洗、统一字段、内容哈希、去重与变更检测
  • 地区、岗位方向、阶段和专业限制规则筛选
  • 来源、样例更新时间、验证状态和质量提示
  • 缺少数据库或外部接口时自动进入脱敏样例模式

能力边界：这是数据自动化、规则筛选、信息管理和产品化展示项目；不包含Agent、大模型、智能推荐或岗位成功率功能。

数据流程

公开入口→合规采集/导入→清洗标准化→ 去重变更→规则筛选→质量提示→来源回查
MVP

来源配置、基础采集接口、清洗与统一字段。

规则化

毕业年份、地区、方向、阶段、专业限制、去重与变更检测。

公开版

无需数据库与Key的脱敏样例模式，补充来源和质量提示。

03 / CONCEPT PROPOSAL
Concept Proposal / 创新产品概念方案 · 未开发上线

AI + AUTOMOTIVE · MULTI-AGENT CONCEPT

DriveMate

面向车主的多Agent智能出行与车况助手。

查看2页概念方案 → 下载概念PDF
目标用户

城市通勤

需要把路线、日程、天气与补能协调到一次任务中。

目标用户

家庭出行

多人、行李、儿童与到达时间让出发准备更复杂。

目标用户

长途驾驶

需要持续关注车况、续航、补能与异常风险。

核心问题

传统助手缺少连续执行

信息分散在地图、天气、日程、车辆与充电站系统。

ORCHESTRATOR DriveMate 主Agent

理解复合任务、拆分步骤、选择工具、汇总事实，并在关键操作前请求确认。

出行规划Agent地图 / 交通 / 天气
车辆状态解释Agent电量 / 胎压 / 维保
补能规划Agent续航 / 充电站 / 停留
日程与提醒Agent日历 / 出发提醒
应急支持Agent异常解释 / 专业服务

典型用户旅程

01提出复合任务

“明天上午带家人从上海去苏州……”

02读取事实

日程、天气、交通、车辆电量、胎压与维保状态。

03协同规划

估算出发窗口、路线与补能候选，并标记数据来源。

04风险与确认

先展示车辆异常和关键假设，再请求用户确认。

05形成计划

输出出发时间、路线、补能点、提醒和应急建议。

SAFETY BOUNDARY

安全边界

  • 不直接执行高风险车辆控制
  • 关键操作需要用户确认
  • 区分车辆事实数据与模型推断
  • 车辆异常优先建议联系专业服务

EVALUATION

评测指标

任务完成率工具调用准确率信息事实性 用户确认次数响应时间用户满意度高风险错误率
